# SECURITY.md — Security Architecture, RBAC & Data Privacy

## 1. Security Architecture Overview

Security for the **Seva Sphoorthi Volunteer Portal** is founded upon the principle of **Least Privilege** and **Zero Trust at the Client Boundary**.

```
    [ Flutter Client ]
           │
           │ 1. Firebase Auth Token (Bearer)
           ▼
    [ Backend / Cloud Run API ]
           │
           │ 2. Role Claim & Payload Validation
           ▼
    [ Cloud Firestore & Storage ] ◄── 3. Firestore & Storage Security Rules
```

---

## 2. Role-Based Access Control (RBAC) Matrix

Users possess one of three distinct roles embedded in their Firebase Custom Claims:
1. `VOLUNTEER`: Standard registered volunteer.
2. `COORDINATOR`: Field organizer who manages local opportunity rosters and verifies attendance.
3. `ADMIN`: Full administrative control across users, approvals, and legal verification.

| Permission / Action | `VOLUNTEER` | `COORDINATOR` | `ADMIN` |
| :--- | :---: | :---: | :---: |
| View Published Opportunities | ✅ | ✅ | ✅ |
| Submit Application / Apply | ✅ | ❌ | ❌ |
| Edit Own Profile & Skills | ✅ | ✅ | ✅ |
| View Own Background Check Status | ✅ | ✅ | ✅ |
| Upload Identity Document | ✅ | ❌ | ❌ |
| Create Draft Opportunity | ❌ | ✅ | ✅ |
| Approve Opportunity for Publication | ❌ | ❌ | ✅ |
| Approve Volunteer Background Check | ❌ | ❌ | ✅ |
| Manage Roster & Confirm Volunteers | ❌ | ✅ | ✅ |
| Verify Volunteer Service Hours | ❌ | ✅ | ✅ |
| Access Full Administrative Reporting | ❌ | ❌ | ✅ |

## 3. Firestore Security Rules Blueprint (`firestore.rules`)

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    
    // Helper functions
    function isAuthenticated() {
      return request.auth != null;
    }
    
    function isOwner(userId) {
      return isAuthenticated() && request.auth.uid == userId;
    }
    
    function isAdmin() {
      return isAuthenticated() && request.auth.token.role == 'ADMIN';
    }
    
    function isCoordinator() {
      return isAuthenticated() && (request.auth.token.role == 'COORDINATOR' || isAdmin());
    }

    // Users Collection
    match /users/{userId} {
      allow read: if isOwner(userId) || isCoordinator();
      allow write: if isAdmin();
      allow update: if isOwner(userId) && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['role', 'status']);
    }

    // Volunteer Profiles Collection
    match /volunteer_profiles/{userId} {
      allow read: if isOwner(userId) || isCoordinator();
      allow create: if isOwner(userId);
      allow update: if isOwner(userId) && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['identityVerified', 'backgroundCheckStatus']);
      allow write: if isAdmin();
    }

    // Opportunities Collection
    match /opportunities/{opportunityId} {
      allow read: if isAuthenticated();
      allow create: if isCoordinator();
      allow update: if isCoordinator() && resource.data.createdBy == request.auth.uid;
      allow write: if isAdmin();
    }

    // Applications Collection
    match /applications/{applicationId} {
      allow read: if isAuthenticated() && (resource.data.volunteerId == request.auth.uid || isCoordinator());
      allow create: if isAuthenticated() && request.resource.data.volunteerId == request.auth.uid;
      allow update: if isCoordinator();
      allow write: if isAdmin();
    }

    // Assignments Collection
    match /assignments/{assignmentId} {
      allow read: if isAuthenticated() && (resource.data.volunteerId == request.auth.uid || isCoordinator());
      allow write: if isCoordinator();
    }

    // Notifications Collection
    match /notifications/{notificationId} {
      allow read: if isOwner(resource.data.userId);
      allow update: if isOwner(resource.data.userId) && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['read']);
      allow write: if isAdmin();
    }

    // Default deny
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

## 4. Sensitive Data Handling & Identity Verification

1. **Document Storage Security**:
   - Volunteer identity documents (Aadhaar, Passport, Drivers License) must be stored in private, non-public Firebase Storage buckets.
   - Access to documents requires temporary signed URLs generated by the backend with an expiration limit of 15 minutes.
   - Direct public access to `/identity_docs/` is blocked at the Storage Rules layer.
2. **Personal Identifiable Information (PII)**:
   - Sensitive demographics (DOB, full residential address, phone numbers) are never exposed in public opportunity roster queries.
   - Roster views visible to coordinators display only verified First Name, Initial, and approved skill tags.

---

## 5. AI / LLM Data Privacy Directives

1. **Zero PII Sent to LLMs**:
   - Prompts sent to the AI Layer for opportunity matching or recommendations must never include real user phone numbers, email addresses, national identity numbers, or street addresses.
   - Prompts must only receive anonymized capability tokens (e.g. `skills: ["Logistics", "Teaching"]`, `city: "Bengaluru"`, `availability: ["WEEKENDS"]`).
2. **Non-Authoritative AI Output**:
   - Matching scores produced by Gemini/LLM are strictly advisory.
   - The AI cannot trigger autonomous approvals or reject volunteer applications.

---

## 6. Rate Limiting & Abuse Prevention

- **API Rate Limiter**: 180 requests/minute per authenticated user IP for general REST endpoints.
- **OTP Verification Limit**: Maximum 5 OTP attempts per phone number per window to mitigate brute-force and spoofing.
- **Resend Cooldown**: Enforced 25-second cooldown between verification code dispatches.
- **Input Validation**: All incoming payloads are sanitized and validated before database persistence.

---

## 7. Phone Authentication & Zero Plaintext OTP Guarantee

1. **Production Authority**:
   - Phone Number → Firebase Phone Authentication → SMS Verification → Firebase ID Token → API Bearer Authorization.
   - Dedicated server-side Firebase token validation confirms claims via Firebase Admin SDK.
2. **Confidentiality Enforcement**:
   - OTP values are **never logged** to stdout, server logs, or monitoring traces.
   - OTP values are **never returned** in API responses or HTTP payloads.
   - OTP values are **never stored in plaintext** in memory, databases, or client-side storage.
   - Resend requests enforce a strict 25-second cooldown, and verification is temporarily locked after 5 failed attempts.

---

## 8. Google Play Store Reviewer Access Policy

1. **Reviewer Credentials Specification**:
   - In compliance with Google Play Store 2-step authentication review guidelines, dedicated reusable reviewer credentials (`REVIEWER_PHONE_NUMBER` / `REVIEWER_OTP`) are supported via environment configuration.
   - Reviewer credentials grant **volunteer-level access ONLY**.
   - Reviewer accounts possess **zero administrative privileges**, zero coordinator abilities, and zero financial/donation manipulation capabilities.
   - Credentials and test OTPs are **never hardcoded** in client APK/AAB or repository source files.
